# CorpSol — контроль и геймификация работы колл-центра

[![Проверки](https://github.com/adiletpn/CorpsolApp/actions/workflows/ci.yml/badge.svg)](https://github.com/adiletpn/CorpsolApp/actions/workflows/ci.yml)

Монорепозиторий: единый бэкенд, веб-панель для руководителей и мобильное приложение для менеджеров.

```
apps/api       NestJS + Firebase (Firestore, Auth) — вся бизнес-логика и интеграции
apps/web       веб-панель: супер-админ, директор, HR, РОП
apps/mobile_flutter  Flutter — приложение МОПа (скан QR, табель, работа,
               сделки, зарплата, рейтинг, награды)
packages/shared общие роли, права, геометрия геозоны, формат QR
```

## Роли

| Роль | Что видит и может |
|---|---|
| Супер-админ | учётные записи, настройки, офисы, терминалы, интеграции |
| Директор | сводная аналитика: звонки, посещаемость, оклады и бонусы |
| HR (ЧР) | приём и увольнение сотрудников, открепление устройств |
| РОП | выполнение плана отделом и каждым сотрудником, звонки, посещаемость |
| МОП | только свои посещения, бонусы, оклад, офферы, звонки, достижения + общий план отдела |

Матрица прав описана один раз в [packages/shared/src/roles.ts](packages/shared/src/roles.ts)
и используется и гвардами бэкенда, и меню клиентов — права не расходятся между слоями.

## Контроль прихода: четыре фактора

Отметка засчитывается, только когда совпадает всё сразу:

1. **Привязанное устройство.** Аккаунт закреплён за одним телефоном. Вход со второго
   отклоняется и создаёт заявку на перепривязку — её подтверждает HR. Один телефон
   нельзя закрепить за двумя сотрудниками.
2. **Живой QR-код.** Терминал в офисе показывает код, который меняется каждые 30 секунд
   (HMAC от секрета терминала и номера временного окна). Секрет не покидает сервер,
   в QR не попадает. Сфотографированный код протухает раньше, чем его перешлют коллеге.
3. **Геозона.** Координаты должны попадать в радиус офиса, причём погрешность
   трактуется не в пользу сотрудника: засчитываем, только если он внутри зоны
   даже в худшем случае. Координаты с точностью хуже 100 м отклоняются.
4. **Офисный Wi-Fi** (опционально). Если для офиса заданы BSSID точек доступа,
   телефон должен быть подключён к одной из них.

Подмена геолокации: Android сообщает флаг mock-location, приложение его передаёт,
сервер блокирует отметку. На iOS такого флага нет — там защиту держат остальные три фактора.

### Офисный Wi-Fi на iOS

Под Android фактор работает сразу. На iOS адрес точки доступа закрыт
разрешением `Access Wi-Fi Information`, которое Apple выдаёт только
идентификаторам приложений, где его включили вручную. Пока это не
сделано, приложение честно отправляет пустое значение, и сервер
отклоняет отметку, если для офиса заданы сети.

Поэтому **не заполняйте сети Wi-Fi у офиса, пока фактор не включён
на обеих платформах** — иначе владельцы айфонов перестанут отмечаться.
Панель предупреждает об этом рядом с полем.

Чтобы включить:

1. В кабинете разработчика Apple → Identifiers → `kz.corpsol.corpsolMobile`
   → отметить **Access Wi-Fi Information** и сохранить.
2. Добавить в три конфигурации цели Runner строку
   `CODE_SIGN_ENTITLEMENTS = Runner/Runner.entitlements;`
   (файл [Runner.entitlements](apps/mobile_flutter/ios/Runner/Runner.entitlements)
   уже лежит готовым).
3. Пересобрать и проверить, что подпись проходит.

## Запуск

Всё поднимается локально на эмуляторах Firebase — облачный проект не нужен,
данные никуда не уходят.

Разово:

```bash
brew install openjdk        # эмулятор Firestore работает на Java
npm install -g firebase-tools
npm install
npm run build:shared
```

Дальше четыре окна терминала:

```bash
./scripts/dev.sh emulators   # Auth :9099, Firestore :8080, интерфейс :4000
./scripts/dev.sh seed        # справочники и сотрудники
./scripts/dev.sh api         # бэкенд :3001
./scripts/dev.sh web         # панель :3000
```

Сид создаёт справочники и сотрудников, но не историю работы — экраны
приложения останутся пустыми. Чтобы было что показывать:

```bash
cd apps/api
FIRESTORE_EMULATOR_HOST=localhost:8080 \
FIREBASE_AUTH_EMULATOR_HOST=localhost:9099 \
npx ts-node scripts/demo-month.ts
```

Скрипт наполняет текущий месяц сменами, звонками, сделками, планами
и расчётом зарплаты для каждого менеджера.

Мобильное приложение запускается отдельно — см. раздел ниже. Ему нужен
адрес машины в локальной сети: `localhost` с телефона ведёт в сам телефон.

Сид создаёт учётки с общеизвестным паролем, поэтому против боевого проекта
он падает намеренно — обойти можно только явным `ALLOW_PRODUCTION_SEED=yes`.

## Тесты

Проверки идут одной командой на весь монорепозиторий:

```bash
npm test          # бэкенд и панель
npm test -w @corpsol/web   # только панель
```

Приложение МОПа проверяется отдельно: `cd apps/mobile_flutter && flutter test`.


Тесты бэкенда идут без эмулятора: Firestore и Firebase Auth подменяются
реализациями в памяти ([fake-firestore.ts](apps/api/test/fake-firestore.ts)).
Поднимать эмулятор ради проверки подписи QR или разбора выгрузки звонков —
несоразмерная цена, а Java в CI не нужна вовсе.

```bash
npm test -w @corpsol/api
```

Покрыты прежде всего места, где ошибка стоит денег или доступа:

| Набор | Что проверяет |
|---|---|
| `employees-service` | выдача ролей, согласованность учётки и карточки, закрытие доступа при увольнении |
| `adjustment-service` | опоздание пересчитывается по графику: поставить «вовремя» вручную нельзя |
| `absence-service` | кому ставится прогул, что задача не затирает, пояса организаций |
| `schedule-resolver` | приоритет личного графика, срок действия |
| `audit-service` | отбор ручных обходов контроля, автор события, порядок и предел выборки |
| `payroll`, `payroll-service`, `bonus-rules-service` | пороги премий, штрафы, предел удержания, отбор правил |
| `analytics-service` | область видимости отделов, отсутствие плана против проваленного |
| `gamification-service` | состав рейтинга, границы периода, своё место в таблице |
| `schedules-service` | ночные смены, срок действия графика, чужой график не удалить |
| `device-binding`, `geofence`, `terminal-token` | четыре фактора отметки прихода |
| `kcell-parser`, `bitrix-mapper`, `calls-import` | разбор выгрузок и защита от дублей |
| `work-numbers-service` | один рабочий номер — один сотрудник, формат номера |

Панель проверяется в jsdom: экран рисуется целиком, а сеть подменяется —
так видно не только разметку, но и то, что уходит на сервер.

| Набор | Что проверяет |
|---|---|
| `session`, `shell` | вход, обработка истёкшего токена, состав меню по роли |
| `employees`, `schedules`, `absences` | формы найма и графиков, копейки в окладе |
| `payroll`, `plans` | дробные проценты и суммы доходят до сервера без потерь |
| `offers` | подтверждает сделку руководитель, в выручку идёт только принятая |
| `overview` | РОП не запрашивает сводку по компании; план без цели не «ноль» |
| `calls`, `work-numbers` | доля дозвонов, чтение номеров, закрепление за сотрудником |
| `audit` | ручные обходы контроля отбираются на сервере, а не в браузере |
| `leaderboard`, `achievements` | места и отрыв, расшифровка очков, прогресс наград |
| `devices`, `settings`, `integrations` | открепление телефона, радиус офиса, маскировка вебхука |
| `period` | деньги, проценты, длительность и телефоны в человеческом виде |

Проверка типов — `npm run typecheck`; тесты входят в неё, поэтому ошибка
в самом тесте не проходит незамеченной.

## Прогулы проставляются сами

Каждую ночь в три часа задача проходит по организациям и отмечает тех, кто
должен был выйти по графику, но не отметился. Без неё день без отметки
остаётся дырой: в табеле его просто нет, в расчёт зарплаты он не попадает,
и невыход ничем не отличается от выходного.

Что задача намеренно не делает:

- **не трогает день, по которому уже есть запись** — ни отметку прихода,
  ни выходной, ни правку руководителя затирать нельзя;
- **не ставит прогул без графика** — неизвестно, должен ли был человек выйти,
  а наказывать по догадке нельзя;
- **не ставит за дни вне срока работы** — принятому в среду не прилетит
  прогул за понедельник.

Дата считается по часовому поясу каждой организации: в одно и то же мгновение
у одной уже вчера, а у другой ещё сегодня. Записи помечаются источником
`AUTO_ABSENCE`, поэтому в отчётах и в приложении отличаются и от скана,
и от ручной правки.

Если задача не отработала — сервер перезапускали, база была недоступна —
день догоняется вручную: раздел «Прогулы» в панели или
`POST /attendance/mark-absences`.

### Несколько экземпляров сервера

Расписание живёт внутри процесса бэкенда, поэтому в трёх экземплярах оно
сработает трижды. Чтобы работу делал один, прогон берётся замком: перед
обходом организации создаётся документ в `jobRuns` с ключом из задачи,
организации и даты. Ключ уже занят — значит, кто-то взялся раньше, и
остальные просто отступают. Договариваться между собой серверам не нужно:
гонку разрешает сама база, как и остальные ограничения уникальности здесь.

Упавший прогон снимает замок за собой — иначе один сбой закрыл бы день
навсегда, и прогулы пришлось бы доставлять руками. Ручной запуск замок
не проверяет: он и существует ровно для тех случаев, когда с ночным
прогоном что-то пошло не так.

## Документы для бухгалтерии

Табель и расчётные листы выгружаются из панели файлом: бухгалтеру нужен
документ к ведомости, а пересчитывать руками то, что система уже
посчитала, — верный способ получить расхождение.

Формат — CSV, потому что его открывает Excel без плясок с установкой.
Три вещи, без которых файл был бы бесполезен:

- **Метка кодировки в начале.** Без неё Excel читает кириллицу
  в однобайтовой кодировке системы, и все фамилии приходят мусором.
- **Точка с запятой как разделитель.** В русской локали запятая стоит
  внутри чисел, и по ней колонки разъехались бы.
- **Апостроф перед `=`, `+`, `-`, `@`.** Имя сотрудника приходит из формы,
  и туда можно вписать формулу нарочно — открытый у бухгалтера файл
  выполнил бы её без вопросов.

Время прихода в табеле местное, по часовому поясу организации: бухгалтер
сверяет его с графиком, где стоит 09:00, а не 04:00 по UTC. Удержания
в расчёте идут со знаком минус, чтобы колонка складывалась сама.

## События сами находят человека

Часть событий никого не зовёт. Заявка на смену телефона блокирует
сотруднику вход и висит, пока ЧР случайно не откроет нужный экран.
Расчёт за месяц готов, а человек об этом не знает.

Почты и пушей в системе нет намеренно: для них нужны внешние службы,
ключи и согласия. Запись ложится в базу, панель показывает её
колокольчиком — этого хватает, чтобы заявка не пролежала неделю.

Уведомление адресуется человеку, а не роли: иначе непонятно, кто уже
прочитал и кто взялся за дело. На роль их рассылается столько, сколько
в ней людей.

Ключ записи детерминированный — повторная обработка того же события
не плодит копии и не возвращает прочитанное обратно в непрочитанные.

**О черновике расчёта сотруднику не сообщают.** Пока лист не утверждён,
суммы ещё изменятся пересчётом; «зарплата готова» дважды за месяц
читается как ошибка в расчёте. Поводом служит утверждение
(`POST /payroll/:userId/approve`), оно же фиксирует цифры.

## Звонки добираются сами

Раз в час задача проходит по организациям с подключённым Bitrix24 и
дотягивает звонки с последней точки. Без этого выгрузку надо запускать
руками, а значит — не запускать вовсе: в понедельник никто не вспомнит
про пятницу, и планы по звонкам покажут ноль у тех, кто работал.

Отрезок замка — организация и текущий час, так что повторный запуск
внутри часа ничего не делает. Недоступный портал одной компании не
оставляет без звонков остальные: ошибка пишется в саму интеграцию,
её видно в панели.

Замок общий с ночной простановкой прогулов — [job-lock.service.ts](apps/api/src/common/jobs/job-lock.service.ts).

## Перебор упирается в предел частоты

Открытых маршрутов два: проверка живости и выдача QR для экрана
терминала. Второй принимает токен, и хотя подобрать 32 байта нельзя,
долбить его можно бесконечно, накручивая чтения базы.

Экран спрашивает код раз в тридцать секунд; предел в две дюжины
за минуту покрывает перезагрузку страницы и сбои сети, но перебор
останавливает. За обратным прокси клиент определяется по заголовку —
без этого все запросы выглядели бы как один и предел срабатывал бы
сразу на всех.

Счётчик живёт в памяти процесса: в нескольких экземплярах предел
умножается на их число. Для защиты от перебора этого достаточно,
а общий счётчик стоил бы обращения к базе на каждый честный запрос.

## Журналы отдаются страницами

Звонков за месяц в колл-центре — тысячи на человека и десятки тысяч
на отдел. Журнал отдаётся по пятьдесят записей, дальше — по кнопке.

Курсором служит время начала последней показанной записи, а не смещение
страницы: за время листания приходит импорт, записи сдвигаются, и часть
звонков сотрудник не увидел бы вовсе.

**Сводка при этом считается по всему периоду**, отдельным запросом.
Доля дозвонов, посчитанная по первой странице, — это просто неверное
число, и видно это было бы не сразу.

## Доступ к базе

Правила в [firestore.rules](firestore.rules) запрещают клиентам обращаться
к Firestore напрямую. Вся работа с данными идёт через бэкенд, который ходит
в базу с правами администратора и проверяет права сам.

Это не перестраховка: ключ приложения Firebase публичен и лежит в любом
собранном клиенте. Открой коллекции на чтение — и сотрудник прочитает чужие
оклады в обход проверок, а заодно подделает себе отметку прихода.

Составные индексы перечислены в [firestore.indexes.json](firestore.indexes.json).
Запрос с несколькими условиями и диапазоном по дате Firestore без индекса
отклоняет, поэтому список покрывает все выборки из сервисов.

## Источники данных по звонкам

Импорт устроен адаптерами, источник подключается независимо:

- **Bitrix24** — REST API по вебхуку, звонки и сделки тянутся инкрементально.
- **Kcell** — выгрузка детализации (CDR) из кабинета, разбор файла и сопоставление
  рабочих номеров с сотрудниками через `ExternalIdentity`.

Повторный импорт одной и той же выгрузки не создаёт дублей: ключ идемпотентности —
пара `(source, externalId)`.

## Развёртывание

Локально всё работает на эмуляторах. Для боевого запуска нужен облачный
проект Firebase и место, куда положить два образа. Порядок шагов —
в [docs/deploy.md](docs/deploy.md): проект Firebase, правила и индексы,
первый администратор, образы, настройка через панель и сборка приложения.

Коротко:

```bash
firebase deploy --only firestore:rules,firestore:indexes
npm run bootstrap -w @corpsol/api   # организация и первый администратор
git tag v1.0.0 && git push origin v1.0.0   # CI соберёт и выложит образы
```

Перед первым выпуском задайте секреты репозитория (Settings → Secrets →
Actions): `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_FIREBASE_API_KEY`,
`NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`,
`NEXT_PUBLIC_FIREBASE_APP_ID`. Это ключи панели: они попадают в бандл
на сборке, поэтому нужны именно там, а не в настройках контейнера.

Проверить сборку целиком можно на своей машине до выкладки:

```bash
cp apps/api/.env.example .env.docker   # заполнить ключами облака
docker compose up --build
```

### Чего делать нельзя

**Не запускайте сид против боевого проекта.** Он создаёт учётки
с общеизвестным паролем и для этого заблокирован намеренно. Для боевого
проекта есть `npm run bootstrap`: одна организация, один администратор
и пароль, показанный ровно один раз.

**Не кладите ключ сервисного аккаунта в репозиторий.** Он даёт полный
доступ к базе в обход всех правил.

**Не разворачивайте приватный ключ на несколько строк.** Он остаётся
одной строкой с экранированными `\n`; иначе Admin SDK молча не пройдёт
подпись, и видно это будет только на боевом проекте.

## Мобильное приложение

Приложение МОПа — `apps/mobile_flutter`, на Flutter. Прежняя версия
на Expo React Native убрана: Flutter-сборка установлена на живое
устройство, держать два приложения рядом больше незачем. История
прежней версии осталась в репозитории.

```bash
cd apps/mobile_flutter
flutter pub get
flutter run --dart-define=API_URL=http://<IP-машины>:3001/api \
            --dart-define=FIREBASE_API_KEY=... \
            --dart-define=FIREBASE_PROJECT_ID=... \
            --dart-define=FIREBASE_APP_ID=... \
            --dart-define=FIREBASE_AUTH_DOMAIN=... \
            --dart-define=FIREBASE_SENDER_ID=...
```

Нужен именно адрес машины в локальной сети: `localhost` с телефона ведёт
в сам телефон. Для эмулятора Firebase Auth добавьте
`--dart-define=FIREBASE_AUTH_EMULATOR_HOST=<IP>:9099`.

Настройки передаются через `--dart-define`, а не через файл: ключи Firebase
публичны по своей природе, но так одна и та же сборка собирается под эмулятор
и под облако без правки кода.

Экраны: приход с отметкой ухода, сделки, зарплата, работа (план отдела
и свои звонки), рейтинг, награды. Светлая и тёмная темы переключаются
кнопкой на главном экране, выбор запоминается.

Что уже проверено: приложение собирается с подписью и **ставится
на физическое устройство** (iPhone 13, iOS 18.7.8), вход и все вкладки
прогоняются сквозным тестом против живых эмуляторов, анализатор чистый.
Под Android сборка пока не проверялась — в SDK на машине разработчика
нет platforms и build-tools.

Установка на подключённое устройство:

```bash
flutter build ios --debug --dart-define=API_URL=http://<IP-машины>:3001/api ...
xcrun devicectl device install app --device <идентификатор> build/ios/iphoneos/Runner.app
```

Идентификатор устройства показывает `xcrun devicectl list devices`.
Подпись настроена автоматическая, команда разработчика уже прописана
в проекте.

Сканирование QR проверяется только на устройстве: в симуляторе камеры нет.

Минимальная версия iOS — 15.5: её требует Firebase 11. Сканер QR взят
свежий намеренно: версия 5 тянула MLKit, несовместимый с Firebase по
GoogleUtilities, и сборка не проходила вовсе.


Вход идёт через Firebase Auth, сессия сохраняется в AsyncStorage — иначе
пароль пришлось бы вводить при каждом запуске. Токен обновляет сам Firebase,
поэтому своей ротации в клиенте нет.

Экран прихода делает три шага: сканирует QR терминала, снимает свежие координаты
(кешированную позицию не берёт — она может быть получена час назад в другом месте)
и отправляет всё одним запросом. Решение принимает сервер, клиент только показывает
результат — подменить вердикт с телефона нельзя.

Идентификатор устройства переживает переустановку приложения: на iOS он лежит
в Keychain, на Android выводится из ANDROID_ID. Иначе сотрудник снёс бы приложение
и получил «новое устройство» в обход привязки. Этот идентификатор уходит
заголовком `x-device-id` с каждым запросом, а не только при входе.

## Веб-панель и экран терминала

```bash
npm run dev:web    # http://localhost:3000
```

Экран терминала живёт по адресу `/terminal/<id терминала>?token=<токен>` и
опрашивает сервер каждые 30 секунд, перерисовывая QR-код. Обратный отсчёт под
кодом показывает, что экран живой, а не завис на старой картинке.

Токен выпускает администратор:

```
POST /api/attendance/terminal/<id>/access-token
```

Открытое значение возвращается **один раз** — в базе остаётся только хеш.
Повторный выпуск обесценивает предыдущий токен.

Токен намеренно узкий: он открывает исключительно QR-код своего терминала и
никаких других данных. Поэтому монитор в проходной зоне не нужно держать
залогиненным под учётной записью администратора — иначе любой сотрудник
получил бы доступ к админке через открытый браузер.

## Как ограничения уникальности живут без SQL

В Firestore нет уникальных индексов, поэтому каждое такое ограничение выражено
через детерминированный ID документа: если ключ занят, запись просто не создаётся.
Все правила собраны в [collections.ts](apps/api/src/firestore/collections.ts),
чтобы их нельзя было случайно обойти, построив ключ иначе в другом месте.

| Правило | Ключ документа |
|---|---|
| Один телефон — один сотрудник | `devices/{deviceId}` |
| Одна отметка на сотрудника в день | `attendance/{userId}_{дата}` |
| Повторный импорт не плодит звонки | `calls/{источник}_{externalId}` |
| Очки не начисляются дважды | `points/{userId}_{причина}_{объект}` |

## Почему устройство проверяется на каждом запросе

Firebase Auth по своей природе разрешает вход с любого числа устройств — сам по
себе он запрет «один аккаунт — один телефон» не обеспечивает. Поэтому привязка
сверяется в [FirebaseAuthGuard](apps/api/src/auth/firebase-auth.guard.ts) на
каждом защищённом запросе, а не только при входе. Мобильный клиент представляет
телефон заголовками `x-device-id` и `x-device-platform`.

Профиль сотрудника кешируется на минуту, чтобы не платить за чтение Firestore на
каждом запросе. Кеш безопасен: увольнение и открепление устройства вызывают
`revokeRefreshTokens`, а токен проверяется с `checkRevoked`, поэтому доступ
закрывается сразу, не дожидаясь истечения кеша.

## Карта API

| Область | Эндпоинты | Кто имеет доступ |
|---|---|---|
| Вход | `POST /auth/session`, `POST /auth/logout`, `GET /auth/me` | все |
| Сотрудники | `GET/POST /employees`, `PATCH /employees/:id`, `POST /employees/:id/terminate` | ЧР, супер-админ |
| Устройства | `GET /devices/requests`, `POST /devices/requests/:id/approve` | ЧР, супер-админ |
| Офисы | `GET/POST /offices`, `PATCH /offices/:id` | супер-админ |
| Терминалы | `GET/POST /terminals`, `POST /terminals/:id/active` | супер-админ |
| Отделы | `GET/POST /departments`, `PATCH /departments/:id` | супер-админ |
| Приход | `POST /attendance/check-in`, `GET /attendance/me` | МОП, РОП |
| Прогулы | `POST /attendance/mark-absences` | РОП и выше |
| Планы | `GET /plans`, `POST /plans` | чтение по роли, постановка — директор |
| Офферты | `GET/POST /offers`, `POST /offers/:id/resolve` | создание — МОП, подтверждение — РОП и выше |
| Зарплата | `GET /payroll`, `POST /payroll/calculate`, `POST /payroll/:userId/approve`, `GET/POST /payroll/rules` | чтение по роли, расчёт и утверждение — директор |
| Рейтинг | `GET /gamification/leaderboard`, `GET /gamification/my-points`, `GET /gamification/achievements` | все |
| Звонки | `GET /calls`, `GET /calls/summary`, `GET/POST/DELETE /calls/work-numbers` | чтение по роли, номера — супер-админ |
| Аналитика | `GET /analytics/company`, `GET /analytics/department`, `GET /analytics/daily` | директор и РОП |
| Выгрузки | `GET /reports/attendance.csv`, `GET /reports/payroll.csv` | по области видимости табеля и зарплаты |
| Уведомления | `GET /notifications`, `GET /notifications/unread-count`, `POST /notifications/read-all` | каждый видит только свои |

Области видимости совпадают с матрицей прав в
[roles.ts](packages/shared/src/roles.ts): МОП видит только себя и общий план
отдела, РОП — свой отдел, директор — компанию целиком.
