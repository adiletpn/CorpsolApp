# Развёртывание

От пустого облачного проекта до приложения в руках сотрудника. Порядок
важен: панель бесполезна без бэкенда, бэкенд — без базы, а приложение
собирается уже под готовый адрес.

Всё, что нужно для работы: проект Firebase (база и вход), два контейнера
(бэкенд и панель) и сборки приложения. Отдельной СУБД, очередей и кеша
здесь нет — их незачем поднимать и некому обслуживать.

## 1. Проект Firebase

В [консоли Firebase](https://console.firebase.google.com) создайте проект,
дальше внутри него:

- **Authentication** → Sign-in method → включите **Email/Password**.
  Остальные способы не нужны: учётки заводит ЧР, самостоятельной
  регистрации в системе нет.
- **Firestore Database** → создайте базу в режиме **production**.
  Регион меняется только пересозданием базы, поэтому выбирайте сразу
  тот, что ближе к пользователям (`europe-west*` для Казахстана).
- **Project settings → Service accounts** → **Generate new private key**.
  Файл понадобится на шаге 3 и больше нигде; в репозиторий он не кладётся.

## 2. Правила и индексы

Правила закрывают клиентам прямой доступ к базе, индексы нужны для выборок
за период. Без индексов запросы отклоняются — это видно сразу, пустыми
экранами и ошибками в логе.

```bash
npm install -g firebase-tools
firebase login
firebase use --add            # выберите созданный проект
firebase deploy --only firestore:rules,firestore:indexes
```

Индексы строятся несколько минут. Пока идёт стройка, выборки за период
возвращают ошибку — это нормально, подождите завершения в консоли.

**Локально индексы не проверяются.** Эмулятор Firestore выполняет любой
запрос, поэтому пропущенный индекс всплывает только в облаке — ошибкой
`FAILED_PRECONDITION` в логе бэкенда. Учтите и направление: диапазон
по дате без `orderBy` идёт по возрастанию, и индекс по убыванию ему
не подходит. После выкладки пройдите все разделы панели.

## 3. Первый администратор

В пустой базе нет ни организации, ни единственной учётки, под которой
можно войти. Заводятся они одной командой.

Демонстрационный сид (`npm run seed`) для этого не годится и против
облака заблокирован намеренно: он создаёт учётки с общеизвестным паролем.

```bash
FIREBASE_PROJECT_ID=corpsol-prod \
FIREBASE_CLIENT_EMAIL=firebase-adminsdk-xxxxx@corpsol-prod.iam.gserviceaccount.com \
FIREBASE_PRIVATE_KEY="$(cat service-account.json | jq -r .private_key)" \
ORGANIZATION_NAME='Колл-центр «Алатау»' \
ORGANIZATION_TIMEZONE='Asia/Almaty' \
ADMIN_EMAIL='admin@example.kz' \
ADMIN_NAME='Иван Иванов' \
npm run bootstrap -w @corpsol/api
```

Пароль скрипт придумает сам и напечатает **один раз** — больше взять его
будет негде. Свой задаётся в `ADMIN_PASSWORD`.

Запуск поверх базы, в которой уже есть организация, отклоняется: вторая
организация, к которой не привязан никто, выглядит как работающая система
и ломается не сразу.

## 4. Бэкенд

Образы собираются по тегу и уезжают в реестр GitHub
([release.yml](../.github/workflows/release.yml)):

```bash
git tag v1.0.0 && git push origin v1.0.0
```

Готовый образ: `ghcr.io/<владелец>/corpsol-api:v1.0.0`. Разворачивается
где угодно, где запускается контейнер, — Cloud Run, Railway, свой сервер
с `docker compose`.

Переменные окружения:

| Переменная | Значение |
|---|---|
| `FIREBASE_PROJECT_ID` | идентификатор проекта |
| `FIREBASE_CLIENT_EMAIL` | из ключа сервисного аккаунта |
| `FIREBASE_PRIVATE_KEY` | оттуда же, переводы строк экранированы как `\n` |
| `PORT` | порт, который слушает контейнер |
| `TELEGRAM_BOT_TOKEN` | токен бота из @BotFather — проверка подписи мини-аппа |

**Ключ сервисного аккаунта даёт полный доступ к базе в обход всех правил.**
Хранить его только в секретах платформы, не в репозитории и не в образе.
В Cloud Run и подобных средах ключ подкладывает сама платформа — тогда
`FIREBASE_CLIENT_EMAIL` и `FIREBASE_PRIVATE_KEY` не нужны.

Живость проверяется без токена:

```bash
curl https://api.example.kz/api/health
```

### Railway и монорепозиторий

Railway при создании сервиса из репозитория сам выбирает сборку
Railpack и прописывает команды вида `npm run start --workspace=...`.
Для монорепозитория это не работает: в собранном образе рабочих
пространств нет, и контейнер падает с «No workspaces found».

Что задать каждому сервису:

| Сервис | `RAILWAY_DOCKERFILE_PATH` | `PORT` |
|---|---|---|
| бэкенд | `apps/api/Dockerfile` | `3001` |
| панель | `apps/web/Dockerfile` | `3000` |
| мини-апп | `apps/telegram/Dockerfile` | `8080` |

И в настройках сервиса **очистить Custom Build Command и Custom Start
Command** — иначе они перекрывают CMD из Dockerfile. `PORT` задаётся
явно и совпадает с портом домена: подставленный Railway порт иначе
разойдётся с тем, куда смотрит домен.

В Watch Paths кроме папки сервиса нужен `/packages/shared/**`:
изменение общих типов без этого не пересобирает сервисы.

### Сколько экземпляров

Ночная простановка прогулов живёт внутри процесса и берёт замок в базе,
поэтому несколько экземпляров безопасны: работу сделает один. Отдельный
планировщик поднимать не нужно.

## 5. Панель

Образ `ghcr.io/<владелец>/corpsol-web:v1.0.0` из того же тега.

Ключи Firebase попадают в бандл **на сборке**, а не в рантайме, поэтому
задаются секретами репозитория — иначе образ соберётся с пустыми
значениями и вход не заработает:

- `NEXT_PUBLIC_API_URL` — адрес бэкенда вместе с `/api`
- `NEXT_PUBLIC_FIREBASE_API_KEY`
- `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
- `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
- `NEXT_PUBLIC_FIREBASE_APP_ID`

Берутся в консоли: Project settings → General → Your apps → Web app.

Эти ключи публичны по своей природе — они видны в любом клиенте. Доступ
ограничивают правила Firestore и проверки на бэкенде, а не их секретность.

Добавьте домен панели в **Authentication → Settings → Authorized domains**,
иначе вход с него будет отклонён.

## 6. Настройка через панель

Войдите под администратором из шага 3 и заведите:

1. **Офис** — адрес, координаты и радиус. Координаты берите с карты по
   входу в здание, не по центру участка. Радиус по умолчанию 120 м
   закрывает погрешность GPS в помещении.
2. **Терминал** — экран у входа, на котором крутится QR. Токен выпускается
   из панели по ссылке.
3. **Отделы** и их **графики** — без графика прогул не ставится: система
   не знает, должен ли был человек выйти.
4. **Сотрудников** — им придут учётки с временным паролем.

Wi-Fi-проверку можно включить позже, добавив BSSID офисных точек. Пустой
список означает, что фактор выключен и работает только GPS.

## 7. Мобильное приложение

Адрес бэкенда и ключи Firebase вшиваются на сборке:

```bash
flutter build ipa \
  --dart-define=API_URL=https://api.example.kz/api \
  --dart-define=FIREBASE_API_KEY=... \
  --dart-define=FIREBASE_AUTH_DOMAIN=corpsol-prod.firebaseapp.com \
  --dart-define=FIREBASE_PROJECT_ID=corpsol-prod \
  --dart-define=FIREBASE_APP_ID=... \
  --dart-define=FIREBASE_SENDER_ID=...
```

Для Android — `flutter build appbundle` с теми же определениями.

Проверьте на живом устройстве до раздачи сотрудникам: вход, скан QR
у терминала, отметку прихода. Геозона и QR на симуляторе не проверяются
по-настоящему — координаты там подставные, а камеры нет.

## Что проверить после развёртывания

- [ ] `GET /api/health` отвечает 200 без токена
- [ ] соседний маршрут без токена отвечает 401
- [ ] вход в панель под администратором проходит
- [ ] заведён офис с настоящими координатами
- [ ] у каждого отдела есть график, действующий с прошлой даты
- [ ] на терминале крутится QR и меняется раз в 30 секунд
- [ ] отметка прихода с телефона в офисе проходит, из дома — нет
- [ ] наутро в табеле появились прогулы у тех, кто не вышел
